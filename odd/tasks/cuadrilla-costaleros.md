# Cuadrilla de costaleros — PWA de gestión de relevos

Objetivo: PWA mobile-first para gestionar pasos, trabajaderas, cuadrillas y relevos de una cuadrilla de costaleros, con backend Payload (MCP para agentes) y motor de reglas de cambios.
Rama: `feature/cuadrilla-costaleros` · Entrega: `ask-on-risk` · Runner: Vitest (dominio) + `tsc`/`next build` (app)

## Specs

- **S1 — Paso con número de trabajaderas elegible.** El usuario debe poder "crear un Paso con sus correspondientes numeros de trabajaderas, el cual sera totalmente elegible su numero". El número de trabajaderas es un entero elegido libremente por el usuario (mínimo 1), se persiste con el Paso, y cada trabajadera queda numerada, ordenada y con lado (izquierda/derecha) y tipo. Un número no entero o ≤ 0 se rechaza con mensaje explícito.
- **S2 — Reglas estrictas de cambio de costaleros, evolutivas.** "tendremos que definir las reglas extrictas para los cambios de los costaleros pero eso lo iremos puliendo poco a poco". Motor de reglas extensible: cada regla tiene id, severidad (`error` | `warning`) y mensaje en español; el conjunto activo de reglas es una lista declarativa que crece sin tocar el motor. Una violación `error` bloquea la operación; `warning` sólo informa. Ninguna regla inicial se inventa: el núcleo arranca con las invariantes estructurales del relevo y acepta reglas nuevas por registro.
  - Catálogo inicial v1 (invariantes estructurales, no reglas de negocio inventadas): `RELEVO_SIN_CUADRILLA_ENTRANTE` (error), `RELEVO_SIN_PUNTO` (error), `TRABAJADERA_SIN_CUBRIR` (error), `COSTALERO_FUERA_DE_CUADRILLA` (error), `COSTALERO_NO_DISPONIBLE` (error), `COSTALERO_REPETIDO_EN_RELEVO` (error), `CUADRILLA_RELEVA_DOS_VECES_SEGUIDO` (error), `PUNTO_DE_RELEVO_DUPLICADO` (warning).
- **S3 — Lógica combinacional de relevos.** "realizar la logica combinacional de sus relevos en el paso". Generar y evaluar planes de relevo de un Paso: qué cuadrilla entra en cada punto del recorrido, cubriendo todas las trabajaderas del Paso, sin dejar puestos vacíos, sin que una cuadrilla releve en dos relevos consecutivos, y con orden determinista. Misma entrada ⇒ mismo plan.
- **S4 — PWA instalable y usable desde el móvil sin red.** "aplicacion sera una PWA" y "casi el 90% sera utilizada desde un movil". Manifest válido, service worker registrado, app instalable, y la acción crítica (registrar/iniciar un relevo) disponible sin conexión, sincronizando al recuperar la red.
- **S5 — Payload + servidor MCP.** "quiero hacer el diseño con payload si puede ser porque creo que tiene servers mcp". Backend Payload 3 embebido en la app, con plugin MCP activo y colección de API keys MCP, de modo que un agente de IA consulte y opere los datos por MCP. `/admin` con login y roles.
- **S6 — Decisión de stack React vs Next.js documentada.** "lo primero sera crear la extructura de lenguaje que debemos decidir entre react o next.js eso debes darme tu las opciones". La decisión queda documentada comparando React (Vite) vs Next.js, con el motivo de la elección, y es reversible por capa (el dominio no depende del framework).
- **S7 — Construcción por modos agénticos.** "quiero que hagas el proyecto con modos agenticos cada uno haga su parte por separado". Cada unidad de trabajo tiene ruta (inline o delegada a un agente), superficie de edición acotada y disjoint, y se integra en un mismo repo validado de forma conjunta.
- **S8 — Asignación de costaleros a las trabajaderas (supuesto).** *Asumido, no pedido explícitamente:* cada relevo asigna costaleros concretos a las trabajaderas del Paso, y la cuadrilla que releva debe aportar el número de costaleros que el Paso exige. Si el supuesto resulta falso, se reescribe S8 y su tarea.

  > Vas a tomar el rol de un diseñador y programador de aplicaciones PWA para lo cual estas altamente capacidato , vamos a crear una aplicacion para la gestion de una cuadrilla de costaleros concretamente para realizar la logica combinacional de sus relevos en el paso . - **L2 — Decisión de stack (2026-11-13):** Next.js 16 (App Router) sobre React, en lugar de Vite + React SPA. Motivo: Payload 3 es Next.js-native (no existe build standalone de Payload sobre Vite), y el usuario pidió Payload; con Next se obtiene React + PWA + MCP en un solo deploy. El dominio queda en TypeScript puro sin dependencias de framework para que la reversión sea barata. Alternativa documentada en ADR (T9).
- **L3 — Decisión de base de datos (2026-11-13):** adaptador SQLite (`@payloadcms/db-sqlite`) en dev porque el entorno no tiene Docker ni PostgreSQL; la configuración queda por variable de entorno para Postgres en producción. Supuesto explícito, no requisito del usuario.
- **L4 — Decisión de PWA (2026-11-13):** Serwist (`@serwist/next`) en lugar de `next-pwa`, porque `next-pwa` es webpack-only y no genera service worker bajo Turbopack/Next 16 (falla en silencio). Verificado contra la guía oficial de PWA de Next.js y el paquete publicado.
- **L5 — Enrutamiento agéntico (2026-11-13):** T1, T2, T5, T9, T10 inline (contrato compartido, wiring y verificación son del padre); T3, T4, T6, T7, T8 delegadas en paralelo por superficies de edición disjuntas. El padre conserva la reconciliación y el cierre.
- **L6 — Catálogo de reglas v1 (2026-11-13):** ocho invariantes estructurales (siete `error`, una `warning`), fijadas antes de implementar para que el motor arranque con algo verificable. Se dejan fuera a propósito las reglas de descanso, simetría y calendario de procesión: son las que el usuario quiere "pulir poco a poco" y entran por registro, sin tocar el motor.
